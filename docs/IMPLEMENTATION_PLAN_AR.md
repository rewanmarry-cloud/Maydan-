هذه خطة مبدئية تتغير بعد تدقيق المستودع. لا تعني أن أي مرحلة اكتملت.

| المرحلة | العمل | شرط الانتقال |
|---|---|---|
| 0 | التحقق من حساب GitHub والمستودع والفرع | ظهور `Maydan` فعلياً والقدرة على قراءة ملفاته |
| 1 | تدقيق المستودع والبنية والتاريخ والاختبارات | تقرير موثق بالملفات والنتائج |
| 2 | تثبيت بنية Flutter ونقطة رجوع | خطة معتمدة وفرع عمل |

## تقرير التدقيق الأول المطلوب
على المساعد تقديم:
1. رابط المستودع الكامل، المالك، والفرع الافتراضي.
2. هل المستودع جديد أم فيه ملفات؟
3. شجرة الملفات الأساسية.
4. حالة Git والـcommits الأخيرة.
5. وجود `pubspec.yaml` و`lib/` و`test/` و`android/` و`.github/workflows/`.
6. إصدارات Flutter/Dart وآلية CI إن وجدت.
7. الاعتماديات والتراخيص والتكاليف أو الحدود.
8. الاختبارات الموجودة ونتائجها الفعلية.
9. المشاكل المؤكدة منفصلة عن الاحتمالات.
10. خطة تغيير صغيرة واختبار قبول لكل خطوة، دون تنفيذها بعد.

## ضوابط التغيير
- استخدم branch لكل مرحلة، مثال `feature/maydan-localization-foundation`.
- لا تعدّل `main` مباشرة.
- لا تحذف أو تعِد تسمية ملفات جماعياً قبل جرد المراجع.
- لا تغير schema أو التخزين أو migrations دون خطة حماية بيانات ونسخة رجوع.
- كل PR يشرح الهدف والملفات والسبب والاختبارات والنتائج والمخاطر وما لم يُختبر.
- عند فشل اختبار، احتفظ بالنص الكامل وحدد السبب قبل تعديل الكود.
- سجل القرارات في `docs/DECISIONS.md`.

## قبول APK
- نجاح GitHub Actions موثق.
- رابط Artifact قابل للتنزيل.
- اسم الملف ونوعه وحجمه موضحة.
- تثبيت APK واختبار تشغيله على Android.
- اختبار نقاط الدخول الرئيسية بالعربية والفرنسية والإنجليزية.
- لا يعلن الإصدار جاهزاً قبل تأكيد المستخدم اختباره على الهاتف.
